# Phase 08.1: Security hardening for public deployment - Context

**Gathered:** 2026-10-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 08.1 is security hardening for public deployment. The codebase is live on GitHub and Vercel at https://hellz-dashboard.vercel.app/. Per ROADMAP.md, in-scope items: (1) purge dummies, (2) upgrade generic handles like `owner-handle`, (3) a more sophisticated identification system to prevent attackers hijacking officer/owner privileges, (4) fix the login connection error ("login returns Nao"). Depends on Phase 8. Discussion clarifies HOW to implement within this boundary; new capabilities belong in other phases.

</domain>

<decisions>
## Implementation Decisions

### Phase scope boundary (Area 5)
- **D-01:** Login connection error fix is URGENT OPS, outside 08.1 plans — fixed immediately as production support, before all other 08.1 work.
- **D-02:** Dummy purge, generic handle rotation, and sophisticated identification system are IN 08.1 plans.
- **D-03:** Priority order for the remaining 08.1 items: (a) purge dummies, (b) rotate generic handles, (c) harden identification system. (Login fix leads as urgent ops.)
- **D-04:** No conflict between purging now and observation — observation ends because the site is public (dummy-name exposure on Destaques + rank distortion outweighs observation value).

### Dummy purge execution (SEED-02 gate) (Area 1)
- **D-05:** Purge runs NOW, as part of 08.1 (not deferred to pre-release).
- **D-06:** Purge is an INSIDE-08.1 plan task: run `purge-dummies.sql` via `scripts/apply-seed.mjs` (Management API `/database/query`, the sanctioned live-write path), then run the zero-dummy verification query (four zeros across members/submissions/submission_stats/pin_login_attempts) and re-run smoke matrix after purge.
- **D-07:** Stay purged until release — NO re-seed after purge.
- **D-08:** OpenCode executes `apply-seed.mjs` for the purge; the rotated `SUPABASE_ACCESS_TOKEN` is handed off out-of-band for this operation only, never stored.
- Prior decision carried forward: `purge-dummies.sql` (`supabase/seeds/dummy/purge-dummies.sql`) is idempotent, FK-safe (submissions before members), sentinel-scoped (`dummy-%`).

### Generic handle rotation (WR-06) (Area 2)
- **D-09:** Owner provides new owner/officer/member handles + PINs OUT-OF-BAND (never committed to repo); OpenCode applies via `apply-seed.mjs`.
- **D-10:** `supabase/seeds/whitelist.sql` keeps 3 rows but with REAL handles + fresh hashes (hashes NOT committed — placeholder rows replaced, not removed).
- **D-11:** Committed hashes already in git/GitHub history: rotate + accept history (old hashes remain in history but are superseded/invalid; WR-06 acknowledges this risk; no git history rewrite).
- **D-12:** Smoke scripts referencing `owner-handle`/`officer-handle`/`member-handle` are updated to the new handles (`scripts/smoke-rls.mjs`, `scripts/smoke-rank.mjs`, `scripts/smoke-promotion.mjs`).
- Prior decision carried forward: WR-06 — rotate handles/PINs before inviting real members (credential hashes recoverable from git history). `add_member` stays the ONLY write surface on `members`.

### Sophisticated identification system (privilege hijack protection) (Area 3)
- **D-13:** Biggest hijack risk identified by owner: someone obtains a foreign screenshot of the basic screen of an officer and uses it to claim a handle that is not theirs before the legitimate owner does. **Handle confirmations (setup-pin/claim) must be CRITICAL OPERATIONS with multiple safeguards.**
- **D-14:** Step-up (re-PIN) authentication required for HANDLING actions only — specifically role changes / hierarchy system actions. Ordinary member flows are NOT stepped up.
- **D-15:** Only the OWNER has universal power over the hierarchy system (role changes, member lifecycle).
- **D-16:** Staff handles use a SEPARATE namespace/prefix from member handles (e.g., `stf-` or `off-`); role is still determined by `members.role`, but the prefix visually/logically separates staff.
- **D-17:** The 7-day session JWT is BOUND to device fingerprint (user agent + IP); session invalidated on binding mismatch (requires re-login).
- Prior decision carried forward: current auth = `discord_handle` + 4-digit PIN only, 7-day HS256 JWT carrying `member_role`, no 2FA/email/device binding, no re-auth for sensitive actions. `setup-pin` already requires an identity proof (photo upload) on first claim. Column-level security: `pin_hash` unreachable by any client credential.

### Login connection error ("returns Nao") (Area 4)
- **D-18:** OpenCode has/needs project-ref access (project-ref exists in `supabase/.temp/project-ref`) to investigate and fix.
- **D-19:** Investigation approach: DEPLOY missing Edge Functions (verify-pin/setup-pin/request-access) to the live Supabase project, check function env vars (`NEFOOT_JWT_SECRET`, `NEFOOT_JWT_KEY_ID`, `SUPABASE_SERVICE_ROLE_KEY`), then PROBE the endpoint directly (curl) and end-to-end from the deployed Vercel site.
- **D-20:** Fix strategy: deploy missing functions/env vars, then verify E2E login from the deployed site (smoke probe).
- Prior decision carried forward: `LoginPage.tsx` already treats non-200/non-JSON responses as `NETWORK_ERROR` ('Não foi possível conectar ao servidor'); verify-pin requires both `apikey` and `Authorization: Bearer <anon>` gateway headers.

</decisions>

## Existing Code Insights

### Reusable Assets
- `purge-dummies.sql` — idempotent, FK-safe dummy purge with built-in zero-dummy verification; reusable as the 08.1 purge plan task
- `apply-seed.mjs` — Management API live-write path for applying SQL seeds to the live project (replaces unavailable `supabase db push`); used for purge + handle rotation
- `verify-pin` + `setup-pin` Edge Functions — existing auth functions to extend for step-up re-PIN and device-fingerprint binding
- `_shared/session.ts` — `mintSession` (7-day HS256 JWT), `envConfig`, `DUMMY_HASH` timing-equalization pattern
- `_shared/lockout.ts` — `record_pin_failure` RPC wrapper reused by both verify-pin and setup-pin (single lockout machinery, no second rate-limit)
- `is_dummy_handle()` — dummy sentinel test (`dummy-%`) already enforced in `add_member` and `create_membership_request`; reusable for staff-prefix separation logic
- `whitelist.sql` — placeholder handle rows to be replaced with real handles via apply-seed.mjs
- `LoginPage.tsx` — login flow with NETWORK_ERROR fallback; already treats malformed/non-JSON responses as network errors (CR-02 pattern)

### Established Patterns
- SECURITY DEFINER RPCs + RLS reading `auth.jwt()->>'member_role'`; enforcement never UI-only
- Column-level security: `pin_hash` unreachable by any client credential (explicit projections only, `select=*` fails by design)
- Append-only everywhere: status/active marks, never deletes or overwrites
- Service_role-only RPCs (`claim_pin`, `create_membership_request`); no caller gate by design, grant is service_role only
- 7-day HS256 custom-claim JWT with `kid` header; `NEFOOT_JWT_SECRET` signing key must never be revoked (standby key 6f7657c3)
- No new npm dependencies (STACK.md / ROADMAP out-of-scope); all security work via SQL + existing Edge Function imports

### Integration Points
- `LoginPage.tsx` → `verify-pin` Edge Function → session → `api.ts` (Supabase REST with JWT; RLS reads `member_id`/`member_role` custom claims)
- `apply-seed.mjs` → Supabase Management API `/database/query` → live project (purge + handle rotation execution)
- `whitelist.sql` seed rows → replaced via apply-seed.mjs with out-of-band owner handles
- Step-up re-PIN and device-fingerprint binding integrate into the existing verify-pin/setup-pin/session stack (no new surface)

</code_context>
