# 10.1-02 — Parity re-lock + live apply + verification

## Problem

The unification shipped in 0036 has no standing guard: the round-8 UNIFY probe in
`smoke-card.mjs` has been red since 0018 precisely because nothing re-ran it, and it never
covered `role_rank` or `my_report` anyway. Without a runnable cross-RPC parity gate, the
next partial rewrite re-forks the rating silently — the exact 0018 failure mode.

## Tasks

1. **Commit `scripts/rpc-ovr-parity-audit.mjs`** (read-only, management API, modeled on
   `scripts/rpc-ovr-audit.mjs`): reproduce each of the six live body shapes as SQL
   against `pg_proc`-equivalent math (or simplest: recompute the two bases — the 0024
   rank-basis and the 0029 value-basis — per active member) and report a table:
   display_name, class, role, role_rank-basis OVR, key-filtered rank-basis, value-basis
   OVR, delta. PASS = every OVR-capable member has delta 0 across bases AND no member
   with data goes null on the Ranking basis; exit 1 otherwise. Also print the
   `class_key_stats` combo census (key_rows / keys_1_6 / relevants per combo). No writes,
   no secrets in output.
2. **Extend `scripts/smoke-card.mjs` UNIFY block** (after probe 10c, same fixture member):
   - **10d:** `role_rank` (owner token, `p_function` = the fixture member's role,
     `p_class` = the fixture class) row for member a has
     `ovr === my_card ovr.value` (exact number equality);
   - **10e:** `my_report` (member token) `ovr.value === my_card ovr.value` (exact);
   - keep 10a-10c untouched — after 0036 they must pass again (they were red since 0018).
3. **Apply 0036 to LIVE** via `scripts/apply-seed.mjs` (the sanctioned live-write path —
   no `supabase db push` in this environment; 0012/0028/0029 precedent). Confirm:
   apply output clean, bookkeeping row present, and the PostgREST reload took effect
   (immediate `my_card` call via REST answers 200 with the new value — never
   `no function matches`, the 0035 lesson).
4. **Run the verification battery** against live, in order:
   - `node scripts/rpc-ovr-parity-audit.mjs` → all deltas 0, no key-filter nulls
     (the three High Priest members must now carry a Ranking-basis OVR);
   - `node scripts/smoke-card.mjs` → full battery green INCLUDING 10a-10e, zero residue
     (its cleanup + zero-residue census must report clean);
   - spot-checks through the live REST surface: `get_promotion_public` card OVR for
     SoldierHellz == `my_card` OVR == the Ranking tab row (browser walk);
   - the two owner-sanctioned fixture members (Smoke Criador Um/Dois) are read-only
     subjects here — NOT purged (D-10.1-08); the standing pre-release purge gate is
     unchanged.
5. **Write `10.1-VERIFICATION.md`**: the audit table (before → after), smoke battery
   result, deploy notes, and the owner walk record (owner opens Ranking + Início +
   Painel for one real member and confirms the same OVR everywhere — the round-8
   "universal measurement" ruling holds again). Flag the follow-up note: tier bands
   (D-01/D-02) may need an owner re-look now that unification RAISES several OVRs
   (e.g. a member reading 51 on the Painel card now reads ~94).

## Hard constraints

  `smoke-config.mjs`, zero production credentials in the repo, guaranteed cleanup +
  zero-residue census in `finally`.
- No writes to the live DB except the migration apply itself (smoke fixtures follow the
  existing self-cleaning pattern).
- No client changes in this plan — if the browser walk surfaces a display defect, record
  it in VERIFICATION and stop; do not scope-creep the hotfix.
