# Phase 10.1 CONTEXT — Universal Rating Unification (URGENT, INSERTED 2026-10-27)

**Owner report 2026-10-27:** "why does the OVR from the cards look inconsistent with the OVR from the Ranking tab?"

**Investigation status:** COMPLETE (2026-10-27) — read-only live audit against the production
project, plus static analysis of every migration that last-defined an OVR-producing RPC.
Root cause is proven, measured, and quantified below. This phase is the fix.

## 1. What each surface actually reads

Six RPCs compute OVR. They were supposed to be one contract; today they are two.

| Surface | UI component | RPC (last defining migration) | Points formula live today |
|---|---|---|---|
| Ranking tab | `RankPage` | `role_rank` (0024) | **rank-based** `(below + (ties−1)/2)/(n−1)×99` — pre-Phase-9 |
| Painel player card + PNG export + photo preview | `DashboardPage` / `CardPhotoUpload` | `my_card` (0028) | **rank-based** — pre-Phase-9 |
| Painel OVR hero + 57-stat points | `OvrHero` via `DashboardPage` | `my_report` (0028) | value-proportional (Phase 9, correct) |
| Início/Destaques showcase cards | `PromotionShowcase` / `PromotionCard` | `get_promotion` + `get_promotion_public` (0029) | value-proportional (Phase 9, correct) |
| Stats-Chave top-5 preview | `KeyStatsPage` | `class_top5` (0028) | value-proportional (Phase 9, correct) |
| Solicitações applicant OVR | `RequestReview` | `staff_requests` (0014) | rank-based AND structurally broken (see §4.5) |

The locked spec is value-proportional: `src/lib/rankMath.ts` (re-baselined in Phase 9) and
REQUIREMENTS `SCALE-01`. The rank-based bodies are the pre-Phase-9 formula that migration
0018 was supposed to retire.

## 3. Root-cause chronology (from git history + migration headers)

1. **2026-10-19 — 07.2 round 8 unified the ratings.** Owner ruling (verbatim, in
   `supabase/seeds/live/promotion-rating-unification.sql`): *"Ratings are an universal
   measurement, once calculated they must be displayed equally. the card the player sees
   in the panel must be the same one available in destaques."* `get_promotion` was rebased
   onto the `my_card` basis. At this moment every surface agreed.
2. **2026-10-22 — migration 0018 (Phase 9) swapped the formula in only 3 of 6 RPCs.**
   The plan's "tripod" was `my_report`/`class_top5`/`get_promotion` (09-01-PLAN scope);
   `my_card`, `role_rank` and `staff_requests` were never in it. The three rebased bodies
   moved to value-proportional; the three untouched ones stayed rank-based — silently
   re-breaking the round-8 unification the same day it was Phase-9-sanctioned.
3. **2026-10-23 — hotfixes 0023/0024 fixed the role filter, not the formula.** Both were
   written to repair the 0018 `char_function` backfall (`my_card` showed 18 key cards,
   OVR always null; `role_rank` same) and copy-pasted the pre-Phase-9 formula while doing
   it. The fork survived the fix.
4. **2026-10-24 — migration 0028 fixed the key-set filter in 4 of 6 RPCs.** The
   "relevants are never keys" rule (`selection_order <= 6`) was added to
   `my_report`/`my_card`/`class_top5`/`get_promotion`. `role_rank` and `staff_requests`
   were missed. For any combo with relevants configured (High Priest/suporte: 10 rows,
   High Wizard/mdps: 9), `role_rank`'s `count(*) = 6` gate can never hold → OVR null on
   the Ranking tab while the cards show a number.

## 4. The stacked defects (all must fall in ONE migration)

1. **Formula fork (primary).** `role_rank`, `my_card`, `staff_requests` compute points
   with the pre-Phase-9 rank-percentile formula; the other four use the locked
   value-proportional formula. Same member+stat → two different numbers depending on tab.
2. **Missing `selection_order <= 6` in `role_rank`'s OVR gate.** High Priest/suporte and
   High Wizard/mdps OVR is permanently null on the Ranking tab (3 live members affected).
3. **Cohort population drift.** `my_report` and `class_top5` read `sub.status <> 'rejected'`
   (includes **discarded**) and don't filter **inactive** members; `my_card`/`role_rank`/
   `get_promotion` exclude both. Latent today (the only inactive member with data is a
   lone Assassin Cross; no member's latest-per-stat value changes when discarded are
   excluded) but it re-forks the rating the moment an inactive member shares a
   class+role cohort with actives.
4. **`stat_direction` ignored by the rank-based path.** The rank formula has no
   direction-aware best. No current key set uses a lower-is-better stat, but if an
   officer ever keys `fixed_ct_pct`/`global_cd_pct`/`variable_ct_pct`, the stale path
   scores better players *worse*. Rebasng onto the value-proportional formula (which is
   direction-aware) removes this by construction.
5. **`staff_requests` is missing BOTH filters** — its OVR lateral reads `class_key_stats`
   by `class_name` only (0014 body, predating the 0018 role re-key): since the 0018
   backfill every class holds 18 rows, so `count(*) = 6` can never hold and **every
   applicant OVR on the Solicitações board renders "—" (data insufficient)**. Statically
   proven; not live-witnessed on 2026-10-27 because the pending-requests queue was empty.

## 5. Why nothing caught it

- `scripts/smoke-card.mjs` carries the round-8 UNIFY probe ("my_card ≡ get_promotion, exact
  equality", probes 10a-10c). It has been **red since 2026-10-22** (0018) — but it is not
  wired into `package.json` or any CI gate and was last run before Phase 9.
- `smoke-rank.mjs` (the Phase 9 "tripod re-lock") covers only the three rewritten RPCs.
- The Phase 9 verification checked the three bodies it knew about; the fork is in the
  three it didn't.

## 6. Decisions (D-10.1-xx)

- **D-10.1-01 — Value-proportional is the canonical formula.** It is the locked spec
  (`rankMath.ts`, SCALE-01, the Phase 9 tripod) and it is direction-aware. The fix REBASES
  `role_rank`/`my_card`/`staff_requests` onto it. (Reverting the three correct bodies to
  rank-based would contradict the Phase 9 owner-approved scale and re-break SCALE-01.)
- **D-10.1-02 — One cohort definition everywhere:** latest value per (member, stat) over
  submissions `status not in ('rejected','discarded')`, over **active** members of the
  same class+build-role. `my_report` and `class_top5` move to it; the other four already
  hold it.
- **D-10.1-03 — One key-set rule everywhere:** every OVR gate and every key-stat list read
  is `selection_order <= 6` (the 0028 owner rule). `role_rank` and `staff_requests` join it.
- **D-10.1-04 — `get_promotion`/`get_promotion_public` are NOT touched.** They are already
  canonical; 0029 generated them from the live prosrc and they must stay byte-stable.
- **D-10.1-05 — Byte-faithful supersession, not a helper refactor (considered, deferred).**
  A shared internal SQL helper (e.g. `_member_ovr(member uuid)`) would structurally prevent
  future drift but changes six payloads' risk profile in an urgent hotfix. The established
  supersession pattern (0023/0024/0028/0029) is used instead, and the permanent guard is
  the cross-RPC parity smoke (UNIF-04) — the drift was detected only because no parity
  gate existed; with one, a partial rewrite goes red the day it ships.
- **D-10.1-06 — Migration 0036 + bookkeeping + PostgREST reload notify.** Numbering
  follows 0035. Per the 0035 lesson (STATE.md: the Management API Run Query endpoint does
  not emit the schema-reload NOTIFY), the migration ends with `notify pgrst, 'reload schema';`
  and records its `supabase_migrations.schema_migrations` row.
- **D-10.1-07 — Live apply via the sanctioned path.** No `supabase db push` in this
  environment; apply through `scripts/apply-seed.mjs` (Management API Run Query), then run
  the read-only parity audit + the smoke battery against live.
- **D-10.1-08 — The two live smoke-fixture members (Smoke Criador Um/Dois) are NOT purged
  by this phase.** They are owner-sanctioned until second order (STATE 2026-10-25); the
  phase's verification uses them as read-only parity subjects, and the standing pre-release
  purge gate is unchanged.
