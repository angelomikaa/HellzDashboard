## Warnings

### WR-01: Parity audit's applicant gate skips NULL cohort rows — false-positive audit failure (exit 1) when a configured key stat has zero cohort submissions

**File:** `scripts/rpc-ovr-parity-audit.mjs:489-496` (SQL), gate at `:535`
**Issue:** Section D's `cohort_n_min` uses `select min(ag.n)` over the `left join cohort_agg`. Postgres `min()` ignores NULL inputs, so a key stat with **no cohort row at all** (an active class+function where nobody has ever submitted that stat — e.g. right after an officer swaps in a new key via `set_key_stat_v2`) is silently skipped. The gate

```js
if (Number(r.keys_configured) === 6 && Number(r.key_stats_held) === 6 && Number(r.cohort_n_min) >= 3 && ovr === null)
```

then fires even though the 0036 body correctly rates the OVR null: the body's per-key gate is `coalesce(a.n, 0) >= 3` (0036 staff_requests line 418), and a missing agg row yields 0, not a skipped value. The audit's own `applicant_ovr` recompute in the same query (line 499) uses the correct `coalesce(ag.n, 0)` gate — so the expectation heuristic and the expression it validates disagree with each other. Result: the release gate prints `holds all 6 key stats over a real cohort but applicant OVR is null` and exits 1 for a healthy server, sending the operator chasing a nonexistent defect. (Not live-witnessed: the pending queue was empty at audit time, per 10.1-CONTEXT.)

**Severity rationale:** WARNING, not BLOCKER — the divergence is fail-closed (false alarms only; it can never mask a real regression), but it makes a shipped release gate unreliable and its failure message factually wrong.

**Fix:**
```sql
-- in the D-section query (scripts/rpc-ovr-parity-audit.mjs)
(select min(coalesce(ag.n, 0)) from class_key_stats ks
  left join cohort_agg ag
    on ag.stat_key = ks.stat_key
   and ag.char_class = r.char_class
   and ag.char_function = r.char_function
  where ks.class_name = r.char_class
    and ks.char_function = r.char_function
    and ks.selection_order <= 6) as cohort_n_min
```
With `coalesce(..., 0)`, a missing cohort row counts as 0 — exactly mirroring the body's gate — and the flag then fires only when the OVR genuinely should be non-null.

### WR-02: smoke-rank's per-run officer handle leaves permanent residue on a crashed run — poisons every later run and strands an active officer-role fixture row in production

**File:** `scripts/smoke-rank.mjs:50` (`OFFICER_HANDLE = \`smoke-rank-officer-${Date.now()}\``), cleanup at `:158-170`, hard 4-row expectation at `:299-310`
**Issue:** The officer handle is unique per run "so a crashed prior run cannot 409 the insert" — but `cleanup()` only deletes handles it can enumerate (`zz-rank-a/b/c` + **this** run's `OFFICER_HANDLE`). If a run is hard-killed before `finally` (Ctrl+C, process crash), its officer member row (`char_class = 'ZZRankSquad'`, `active = true`, `role = 'officer'`) survives forever:

1. **Every subsequent run goes red:** the next run recreates class `ZZRankSquad`, and the orphaned officer (still active, still pointing at that class) rejoins the `class_top5` board as an extra null-OVR row. Probe 6's exact expectation `top5rows.length === 4` (changed in this diff from 3 to 4) then fails on every later run until someone manually deletes the orphan — contradicting the file's own discipline ("a crashed prior run must not break this one", "second run must also pass"). smoke-rank has no zero-residue census (unlike smoke-card) to surface this.
2. **Production hygiene/security:** the orphan is an **active, officer-role** member row on the live panel with a guessable handle (`smoke-rank-officer-<timestamp>`) and a 4-digit PIN hash. Rate limiting throttles brute force, but a crashed smoke run permanently leaves a staff-privileged fixture identity in the real member table.

**Severity rationale:** WARNING — test-reliability defect (a single crash permanently bricks the suite) plus live-data residue; requires a crash to trigger, and is a test-tool defect, not production logic.

**Fix:** use a **fixed** handle and let the existing pre-run `cleanup()` do the 409-prevention (exactly the smoke-card pattern: its fixed `smoke-card-officer` is deleted by pre-clean before insert), and extend cleanup to purge legacy timestamped orphans:

```js
const OFFICER_HANDLE = 'smoke-rank-officer' // fixed: pre-run cleanup removes it first — no 409 possible

// in cleanup():
await mgmtQuery(
  `delete from submissions where member_id in (select id from members where discord_handle like 'smoke-rank-officer%');`
)
await mgmtQuery(`delete from members where discord_handle like 'smoke-rank-officer%';`)
await mgmtQuery(
  `delete from pin_login_attempts where discord_handle like 'smoke-rank-officer%';`
)
```
The pattern-delete also sweeps up any orphan already stranded by earlier crashed runs.

### IN-01: Dead branch — `valueParity` can never become false in probe 10b

**File:** `scripts/smoke-card.mjs:713-726`
**Issue:** In the 10b loop, the first condition is `if (!mine || !promo || mine.points !== promo.points || mine.own_value !== promo.value)`. Reaching the `else if (mine.own_value !== promo.value)` branch (line 722) therefore requires `mine.own_value === promo.value` to be both true (to enter the else) and false (to set the flag) — the `valueParity` flag is dead code and the dedicated "value mismatch" detail message is unreachable. The check's outcome is still correct (any value mismatch trips the first branch and fails via `pointsParity`), but the flag and the `pointsParity && valueParity` conjunction are vestigial and misleading to maintainers.
**Fix:** drop the else-if and the flag, or restructure so value mismatches produce their own detail entry:
```js
if (!mine || !promo) { pointsParity = false; detail.push(`${stat_key}: missing row`) }
else if (mine.points !== promo.points) { pointsParity = false; detail.push(`...points ${mine.points} != ${promo.points}`) }
else if (mine.own_value !== promo.value) { valueParity = false; detail.push(`...value ${mine.own_value} != ${promo.value}`) }
```

### IN-03: Audit body-census markers are substring-brittle and under-pinned for my_report/class_top5

**File:** `scripts/rpc-ovr-parity-audit.mjs:113` (`RANK_LEFTOVERS = ['cb.value <', 'ct.value =', 'below', 'ties']`), `:122-123` (BODY_CONTRACT for my_report/class_top5)
**Issue:** (a) The bare substrings `below`/`ties` will false-positive on any future body that legitimately contains those letter sequences inside other words (`priorities`, `entities`, `ties` in a comment). The five 0036 bodies are clean today (verified by grep — zero hits), but the marker choice makes the audit fragile against harmless edits, and a false alarm is a hard exit 1. (b) For my_report/class_top5 the `must` markers were relaxed to `least(greatest(` + `round(` as separate strings (because those bodies' formatting splits the expression). Two loose markers cannot pin the formula — e.g. a regressed body that swaps `a.min_v`/`a.max_v` in the lower/higher CASE, or moves the clamp outside the round, would still pass section A. (Live RPC parity is covered by smoke-card 10d/10e, so this is a depth note on the audit, not a coverage hole in the overall gate.)
**Fix:** use anchored markers (`c.below`, `as ties`, `count(*) filter (where b.value < a.value)`) for the leftovers; for my_report/class_top5, pin the full expression with a whitespace-tolerant check (e.g. normalize `prosrc` by collapsing `\s+` to a single space before matching `least(greatest( round(`, `when 'lower' then o.value / nullif(a.min_v, 0)`, `else o.value / nullif(a.max_v, 0)`).

### IN-04: Probe 9 spawns smoke-rank via a CWD-relative path

**File:** `scripts/smoke-card.mjs:774-775`
**Issue:** `spawnSync('node', ['scripts/smoke-rank.mjs'], ...)` resolves relative to the current working directory, not to the smoke-card module's location. Running the suite from anywhere but the repo root (`node D:\...\scripts\smoke-card.mjs`) fails probe 9 with `exit=null` even though the server is healthy. Also, a spawn failure surfaces only as `exit=null` in the detail (the `spawnSync` `error` property is not inspected).
**Fix:** resolve the path from the module URL and surface spawn errors:
```js
import { fileURLToPath } from 'node:url'
const here = fileURLToPath(new URL('.', import.meta.url))
const rankRun = spawnSync(process.execPath, [`${here}smoke-rank.mjs`], { stdio: 'inherit', env: process.env })
check('9. regression: ...', rankRun.status === 0, `exit=${rankRun.status}${rankRun.error ? ` err=${rankRun.error.message}` : ''}`)
```

### IN-05: Audit header documents a session-env fallback that the code does not implement

**File:** `scripts/rpc-ovr-parity-audit.mjs:56` (doc) vs `:80-81` (code)
**Issue:** The header says `Env (session or .env): SUPABASE_ACCESS_TOKEN / SUPABASE_ACESS_TOKEN`, but the typo spelling is only read from the **.env file** (`envFile.SUPABASE_ACESS_TOKEN`); a session-exported `SUPABASE_ACESS_TOKEN` is silently ignored, and the user gets `missing management token` despite following the documented contract. (The model script `rpc-ovr-audit.mjs:24` has the same gap, so this is inherited, not introduced — but the new header's "session or .env" phrasing makes the mismatch more likely to be hit.)
**Fix:** add the session-env typo as the final fallback, or drop `SUPABASE_ACESS_TOKEN` from the documented session vars:
```js
const MGMT_TOKEN =
  process.env.SUPABASE_ACCESS_TOKEN || envFile.SUPABASE_ACCESS_TOKEN ||
  process.env.SUPABASE_ACESS_TOKEN || envFile.SUPABASE_ACESS_TOKEN
```
