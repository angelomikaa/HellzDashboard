# Phase 10.3 — Artista (Menestrel + Cigana merged cohort)

**Owner request 2026-10-29**: "on the site, we have new submission from menestrel —
however, menestrel and cigana are the same class for the purpose of stats, so they also
must be merged, in a status of exception, all other tabs keep working as they are, except
for the 'menestrel + Cigana' tab. And we must call the merged tab the 'Artista' tab."

Owner scope answers (2026-10-29, via question gate):
1. **All surfaces** show the merged class: Ranking, Personagens, Stats-Chave, Painel,
   Início and the cards.
2. **ONE shared 6-key config** for Artista/Suporte (one config for both classes).
3. **Each member keeps their own class** — the card and the registry keep printing
   "Menestrel" / "Cigana"; only the STATS COHORT becomes "Artista".

## Root cause / current state

The rank engine scopes every cohort by `(members.char_class, members.char_function)` and
every key-stat config by `(class_key_stats.class_name, char_function)`, so a Bard member
and a Gypsy member are two separate cohorts with two separate configs. In this game they
are the SAME job line (Dancer/Bard — the same skills, the same stats), so each sees a
data-insufficient board while the guild's artist data is split in half: Bard/suporte had
0 validated submitters while Gypsy/suporte is data-sufficient.

## Design (the "exception" that must not leak into other classes)

- `public.class_cohort_merges (class_name pk → classes, group_name)` — a class maps to
  at most one STATS GROUP. Seeded `('Bard','Artista')`, `('Gypsy','Artista')`. Any class
  NOT in the table is its own group (that is what keeps every other tab untouched).
- `public.cohort_group(p_class)` — immutable SQL helper returning the group when the
  class is merged, else the class itself.
- `classes` gains the VIRTUAL catalog class `'Artista'` — it satisfies the
  `class_key_stats`/`class_relevant_stats` FK chain and appears in `/classes` (so the
  class filters show it ONCE), while `members.char_class` keeps Bard/Gypsy (a member can
  never be an Artista; the client filters the virtual class out of registration selects).
- Key stats / relevant stats / `class_cohorts` are re-keyed onto the group
  (Artista dps/mdps/suporte, suporte = meta), the Bard/Gypsy rows are removed from the
  stats surfaces, and `class_cohorts` drops from 39 rows (23 meta / 16 dark) to 36
  (22 meta / 14 dark).
- All seven cohort-producing RPCs (`my_report`, `my_card`, `role_rank`, `staff_requests`,
  `class_top5`, `get_promotion`, `get_promotion_public`) are `create or replace` — same
  signatures, same closed payloads, same value-proportional math (never re-derived), with
  ONE systematic change: the cohort key and the key-stat config read go through
  `cohort_group()`, while the payload's own-class fields keep the member's real class.

## Non-negotiables (from AGENTS.md)

- Append-only migration (0038); create-or-replace only; live apply via
  `scripts/apply-seed.mjs`, never the CLI.
- Key-stat CONFIG is never serialised; the merge must not leak the group as a member's
  class; every other cohort behaves exactly as before.
- A regression gate runs the OVR parity audit + the smoke battery after the live apply.
