## Phase Boundary

Phase 07.2 turns the panel's celebration surfaces into a premium EAFC-style showcase grounded in the game, building on the 07.1 token/typography foundation. It delivers: (a) **CARD-01** — member stat cards showing ONLY the 6 class+function key stats, via a leak-safe server design (key-stat CONFIG — weights/toggles — never exposed; which stats are key is now deliberately revealed); (b) **CARD-02/CARD-03** — EAFC Ultimate Team styling with 3-letter abbreviated stat labels and downloadable/shareable JPEG cards; (c) **DSTQ-01** — a bolder, full-bleed immersive Destaques showcase (Impecável-only preserved); (d) **ASST-01** — ROO game assets (class/job imagery from roocamer.gnjoy.game) self-hosted in the repo; (e) **LAYT-01** — a deliberate desktop layout pass across all surfaces; (f) **RANK-02** — an officials+ full-stat OVR-based rank view in its own tab; (g) **RELV-01** — a secondary "relevant" stat tier (unlimited count, never displayed on cards) that governs foco de melhoria.

**Requirement IDs note:** CARD-/DSTQ-/ASST-/LAYT-/RANK-02/RELV-01 requirement text lives in the ROADMAP.md Phase 07.2 entry (REQUIREMENTS.md has not yet been updated for this inserted phase) — the roadmap success criteria are the authoritative requirement text.

## Implementation Decisions

### Key-stat member cards (CARD-01)
- **D-01: Card strip on Painel.** The 6 EAFC key-stat cards render as a hero strip at the top of Painel; the existing 57-stat grouped view stays below unchanged (CMP-01 preserved — no validated surface is taken away).
- **D-02: Pure EAFC anatomy.** Key-stat cards show 3-letter abbreviated label + value + points chip + tier styling ONLY — NO Média/Melhor aggregate line on the key-stat cards. (The full 57-stat view below keeps its current anatomy.)
- **D-03: Leak-safe reveal boundary.** Members see WHICH stats are key (sanctioned reveal — the anti-gaming rationale shifts from hiding key identity to guiding what to grind), but the key-stat CONFIG (weights/toggles/management surface) remains staff-only. Server-side design required: the member payload must be filtered server-side so a tampered client can never obtain key-stat identity beyond what the cards legitimately show, nor any config data. RNK-02 closed-payload discipline re-baselines: existing leak probes asserting "no key-stat identity in my_report" must be re-derived for the new sanctioned reveal (config still never appears).

### Relevant stat tier (RELV-01)
- **D-04: Stats-Chave governance.** The relevant tier is managed on the existing Stats-Chave admin page as a second section, per the same cohort shape as key stats (class today; must reconcile with Phase 9's per-(class, build-role) key configs).
- **D-05: Key/relevant mutual exclusivity + gating (owner-confirmed verbatim semantics):**
  1. A stat is key XOR relevant XOR neither — never both.
  2. Relevant stats can only be selected after all 6 key stats are defined for that class.
  3. If a key stat is deselected, existing relevant stats REMAIN relevant (a vacancy doesn't demote them), but NEW relevant selections are blocked until the key set is complete again (exactly 6).
  4. Promoting a relevant stat into a vacant key slot removes it from the relevant tier ("a relevant stat becomes key when selected").
- **D-06: Visual marking on Stats-Chave.** Key stats are marked red, relevant stats marked YELLOW (owner direction). Note: this is a deliberate exception to 07.1's single-red-accent / no-gold-on-chrome rule (D-01 07.1) — the yellow marking lives on the admin surface as a tier signal, analogous to how tier-gold survived. Implementation should use a dedicated token, not reintroduce the retired `#E3B341` accent.
- **D-07: Foco de melhoria rule.** Foco evaluates key AND relevant stats and picks the ones MOST BEHIND compared to the guild average — filtering out irrelevant stats ("there's no need for an assassin to improve his cura realizada stat"). Top 3 items, behind-first ranking, stable-order tie-break (existing strip rhythm). This replaces the current "3 lowest points" focusCandidates rule. Note for planner: "behind vs average" uses class_average already present in the my_report payload; gap semantics must handle flat vs percentual scales and the negative lower-is-better stats (Fixed CT %, Global CD %, Variable CT %) — a lower-than-average negative stat is BETTER, not behind.

### EAFC card form & JPEG export (CARD-02/CARD-03)
- **D-08: Download scope.** Members download their OWN card from Painel; Destaques lets anyone download any Impecável player's showcase card (the promotion point — share the guild's best on Discord/WhatsApp).
- **D-09: Export contents.** Full identity + 6 key stats: player name, class, build-role, OVR (hero number, Orbitron), the 6 key stats (3-letter label + value + points chip), tier color treatment, Hellz mark. NO guild-average data on the export — it is a celebration artifact that circulates outside the guild. Points chips are sanctioned on the export (guild-internal rank info is accepted as public by this decision).
- **D-10: Portrait EAFC shape.** Classic Ultimate Team card proportions (~2:3 portrait) — OVR + class crest on top, name, 6 stats in the EAFC vertical arrangement.
- **D-11: 3-letter labels — draft + owner review.** OpenCode drafts the full 57-stat pt-BR 3-letter mapping (e.g. Taxa de Crítico → CRC), owner reviews/corrects as a deliverable before it locks into code.
- **D-12: Code-drawn canvas export.** The JPEG is drawn programmatically (Canvas/SVG rendered in code) client-side — zero new npm dependency, pixel-perfect EAFC composition, and no canvas-tainting risk (which pairs with the self-hosted assets decision D-15).

### Showcase cards reconciliation (CARD-01 × get_promotion)
- **D-13: Destaques cards show the key stats.** The showcase card's 6 stats become the player's class+function key stats — same set as the member's own Painel card strip — replacing the current top-6-by-points facets. get_promotion's payload design must follow the same leak-safe server-side shape as D-03 (server decides; no config exposure).

### Destaques premium showcase + ROO assets (DSTQ-01/ASST-01)
- **D-14: Full-bleed immersive register.** Destaques gets an immersive dark hero screen, oversized cards, dramatic imagery — it feels like a game launch site and deliberately breaks the minimal-functional register of the rest of the site (which stays as-is). 07.1 authorizations apply here: neon-grid backdrop, tier accents, Orbitron hero numbers, static glows only (no animation).
- **D-15: Assets self-hosted in the repo** (like h-logo), mirroring the source site's naming scheme (class-f / class-m / class-icon patterns) under src/assets or public. Assets unavailable on the roocamer.gnjoy.game surface should be downloaded directly if possible — the owner notes many class icons are absent from the site and Rebellion is completely omitted there. Hotlinking was rejected (canvas tainting + availability/ToS risk).
- **D-16: Neutral fallback for missing art.** Classes with no official art (e.g. Rebellion) get a tasteful neutral fallback — the Hellz mark or a class-initial monogram tile in tier styling. No broken images, no fake art.
- **D-17: Imagery placement.** Class/job imagery appears on: Destaques full-bleed showcase (card art/hero), the member's EAFC card (class crest), and compact class icons in staff views (Validações queue, Personagens, the new rank view). Login stays as-is (mark + lockup own it). Data-dense member views keep text-first density.

### Officials rank view (RANK-02)
- **D-18: Role-primary boards.** The rank view's primary axis is the BUILD ROLE, not the class — three boards: Dano Físico, Dano Mágico, Suporte — ranked by OVR within the role, with a class filter/selector on top (all classes by default). Owner rationale: build intent is what makes comparisons fair; some classes are impossible to build as damage or as effective support, and class-wide tables would punish off-role builds (Summoner can be all three roles). Class shows as a per-row attribute. Note: OVR is the cross-role comparable currency (same rationale as Phase 9's class-wide promotion top-5).
- **D-19: Table + detail shape.** Sortable table: one row per member (name, class, role, OVR, per-stat columns or expandable detail); a per-player detail view shows all 57 values.
- **D-20: Value + points + avg columns.** Per stat: the member's raw value AND their points (0–99), plus class average for context. This is a deliberate officials visibility expansion (today only the pending-submission queue exposes individual values). Members NEVER see this view — enforcement must be server-side (staff-gated SECURITY DEFINER RPC, not tab-hiding only).

### Desktop layout pass (LAYT-01)
- **D-21: Wide + reflowed grids.** Lift the max-width on wide screens (e.g. max-w-6xl/7xl for data views) and reflow grids: stat cards 3–4 across, rank view full-width table, Destaques hero full-bleed with centered content column.
- **D-22: Everything, one pass.** All surfaces treated consistently: Painel (card strip + grouped stats), Destaques, submit wizard, staff pages (Validações, Personagens, Stats-Chave), the new rank view, login — one breakpoint system.

### Phase 9 reconciliation (planner must address)
- **D-23: Forward-compatible key-stat reads.** Cards show "the 6 key stats of the character's class+function." Today class_key_stats is per class; Phase 9 makes it per (class, build-role) with backfill (zero OVR change on deploy day). The card data path must read whatever config exists at runtime (class-level now, per-combo after Phase 9) so 07.2 needs no rework when Phase 9 lands. Relevant tier governance (D-04/D-05) must likewise survive the Phase 9 re-keying.
