# Phase 10.4: Code Review Report

**Reviewed:** 2026-10-30T19:43:14Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

The SQL surface is well built: `get_lineups()` returns a genuinely closed payload (no stats, points, OVR, key-class config or `pin_hash` reach the wire), both tables are RLS-enabled with SELECT-only grants to `authenticated`, all three RPCs are `SECURITY DEFINER` with an explicit `set search_path = public`, EXECUTE is revoked from `public`/`anon`, no dynamic SQL exists anywhere in the migrations, and `set_lineup_slot`'s vacate→place→return-displaced sequence is correct for every ordering I could construct (including self-swap and cross-raid). The client is equally disciplined: no `dangerouslySetInnerHTML`, every canvas image is a same-origin bundled asset (`iconSrcFor` resolves from a static manifest, never a payload URL), and `asLineupsPayload` builds closed objects so extra server fields are dropped. `tsc -b`, `oxlint` and the 35 lineup tests are green.

The defects are elsewhere. The headline one is that the device-binding guard this phase wires into every officer write (`assert_device_bound`) cannot bind anything: the value it compares against is a non-secret claim *inside the bearer token the caller already holds*, so a replayed token passes by echoing its own claim into the header. Beyond that: a deactivated seated player turns into a nameless "ghost" slot through normal UI use, mirrored concurrent swaps deadlock, the migration invariants hard-fail on legitimately mutable live data, and the client's error/ session handling has several cases where the copy shown is wrong or the session is silently killed.

## Critical Issues (BLOCKER)

### CR-01: `assert_device_bound()` is bypassable by any holder of the token — the device fingerprint is not a secret

**Severity:** BLOCKER
**File:** `supabase/migrations/0041_device_binding_guard.sql:37-49`, `supabase/functions/_shared/session.ts:89-96`, `supabase/functions/_shared/device.ts:10-15`

**Issue:** The guard compares two client-supplied values:

```sql
v_claim  text := coalesce(auth.jwt()->>'device_fp', '');   -- inside the JWT the caller holds
v_header text := public.request_device_fingerprint();      -- X-Device-Fingerprint header
if v_claim = '' or v_header = '' or v_header <> v_claim then raise exception 'device_mismatch';
```

The JWT is handed to the browser and is trivially decodable (`base64url(payload)`), and `device_fp` is a plain, unencrypted claim in it. An attacker who steals a session token reads `device_fp` out of their own token and sends that exact string in `X-Device-Fingerprint`. The comparison succeeds on any machine, with any User-Agent, with no knowledge of the victim's device.

That makes the stated security property false. `device.ts:10-13` and `0041:55-58` both assert that "a stolen session is invalidated from a different device" — it is not. The guard only rejects clients that don't bother to read their own token, i.e. it is an accidental-mismatch detector dressed as an anti-theft control, and this phase is the first to make officer privilege writes depend on it (`0040:215`, `0040:312`). It also does not protect against the honest-client case it appears designed for: SHA-256(userAgent) is guessable/stock per browser build, so even without reading the token a replay from a similarly-configured machine passes.

**Fix:** either drop the false claim, or make the check use a value the client must *possess* rather than one it is *given*:

```sql
-- Option A (minimal, honest): keep the guard as an accident detector only.
comment on function public.assert_device_bound() is
  'Raises device_mismatch when the request fingerprint differs from the session fingerprint claim. NOT a theft control: device_fp is a claim inside the bearer token, so any token holder can replay it.';

-- Option B (real binding): store a per-session secret server-side and compare hashes.
--   login: generate 32 random bytes -> return to client; store sha256(secret) in a
--          sessions table keyed by jti; never put it in the JWT payload.
--   write: assert_device_bound() compares sha256(X-Device-Secret header) to the stored hash
--          (single use / rotate), so a token alone is insufficient.
```

Whatever is chosen, `0041` must stop advertising theft protection until the mechanism actually delivers it, and the phase's D-01 "device-bound" requirement should be re-read as "accident-bound".

## Warnings

### WR-01: A deactivated (or fixture-filtered) seated player renders as a nameless "ghost" slot

**Severity:** WARNING
**File:** `supabase/migrations/0040_battlefield_lineups.sql:104-132` (and `src/features/lineup/LineupPage.tsx:379-391`)

**Issue:** The `slots` CTE joins slot display fields against the **filtered** `roster` CTE:

```sql
slots as (
  select ..., 'display_name', r.display_name, ...
  from lineup_slots s
  left join roster r on r.id = s.member_id      -- roster = active AND not smoke/dummy
)
```

`roster` only contains `m.active` non-fixture members. An officer can deactivate a seated player through the existing Personagens surface (`set_member_active`), and nothing clears `lineup_slots`. The row then keeps `member_id` but returns `display_name: null, char_class: null, char_function: null`. On the client `vacant = slot.member_id === null` is **false**, so `LineupPage` renders a crest plus an empty name span — no `— Vago —`, no name — and `filled`/`N/5` still counts the ghost. The same happens for any seated member whose handle matches `smoke%`/`dummy-%` (see IN-02). This state is reachable through the UI, not just theoretically.

**Fix:** read slot display fields from `members` directly (the filter belongs on the assignable roster only), and/or clear seats on deactivation:

```sql
slots as (
  select s.battlefield, s.party_index, s.slot_index,
         jsonb_build_object(
           'slot_index', s.slot_index,
           'member_id', s.member_id,
           'display_name', coalesce(l.nickname, m.display_name),
           'char_class', coalesce(l.char_class, m.char_class),
           'char_function', m.char_function
         ) as j
  from lineup_slots s
  left join members m on m.id = s.member_id
  left join lateral (
    select h.nickname, h.char_class from member_identity_history h
    where h.member_id = s.member_id order by h.created_at desc, h.id desc limit 1
  ) l on true
)
```

### WR-02: Mirrored concurrent swaps deadlock inside `set_lineup_slot`

**Severity:** WARNING
**File:** `supabase/migrations/0040_battlefield_lineups.sql:247-260`

**Issue:** The function locks the **target** row first (`... where target ... for update`), then locks the **source** row (`... where s.member_id = p_member for update`). Two officers performing mirrored moves — A: move P from S1 into the slot holding X (T2); B: move X from T2 into the slot holding P (S1) — acquire the two row locks in opposite order and Postgres aborts one with SQLSTATE 40P01. The client maps that to the generic "Não foi possível salvar a alteração", so the officer cannot tell a deadlock from a validation failure. No corruption (the transaction rolls back), but it is a real concurrency defect on a surface whose whole point is live editing during a raid.

**Fix:** acquire both row locks in one statement with a deterministic order:

```sql
-- lock both rows (target + the member's current seat) in a single ordered scan
perform 1 from lineup_slots s
 where (s.battlefield = p_battlefield and s.party_index = p_party and s.slot_index = p_slot)
    or (p_member is not null and s.member_id = p_member)
 order by s.battlefield, s.party_index, s.slot_index
 for update;
-- then re-read v_displaced / v_old_* from the locked rows
```

### WR-03: Moving an unassigned player silently unseats the target's occupant, with no UI warning

**Severity:** WARNING
**File:** `supabase/migrations/0040_battlefield_lineups.sql:262-265`, `src/features/lineup/LineupPage.tsx:480-484`

**Issue:** When the chosen player is not seated anywhere, the implementation overwrites the target slot and the occupant simply becomes unassigned (documented in the SQL comment, but not in D-04, which only covers moving a *seated* player). The picker shows a `Raid N · Gx · mover` badge for the player being chosen, but nothing tells the officer that the slot's current occupant will be dropped. During a raid that is an easy way to unseat someone by accident, and the result looks identical to an intentional clear.

**Fix:** surface it in the picker (`{currentMemberName} será removido`) and/or make the server swap the two when the source is unassigned but the officer confirms. Minimum: add the warning text next to "Limpar slot" when `currentMemberId !== null` and the picked member has `assignment === null`.

### WR-04: Four privileged staff RPCs still have no device guard, and `0024` must never be applied as-is

**Severity:** WARNING
**File:** `supabase/migrations/0041_device_binding_guard.sql:16-19` (context: `supabase/migrations/0024_device_binding_enforcement.sql:58-96`)

**Issue:** `0041` creates the guard functions and deliberately leaves `set_member_role`, `set_member_active`, `reset_member_pin` and `add_member` untouched, so the SEC-04 goal ("device-bound staff privilege mutations") remains unenforced for the four most sensitive operations while `0040`'s D-01 wording implies all writes are guarded. Worse, the only file that would add the guard (`0024_device_binding_enforcement.sql`) contains **stub bodies** (`perform public.assert_device_bound(); -- (live body preserved verbatim ...)`) — applying it blanks four live functions. `scripts/apply-seed.mjs` has no applied-version check (`apply-seed.mjs:40-58`), so it will happily run it. The repo therefore carries a one-command landmine aimed at the privilege layer.

**Fix:** replace `0024`'s stubs with `revoke`/no-op text that cannot compile into a destructive `create or replace`, or delete the file and note in `0041` that it supersedes it; then add a real, guard-prepending migration for the four RPCs (dump the live bodies first). Until then, `0041`'s header comment should state that those four remain unguarded *by design*, not just "not applied here".

### WR-05: Every officer write now depends on a User-Agent hash, and a browser auto-update breaks it

**Severity:** WARNING
**File:** `supabase/functions/_shared/session.ts:89-96`, `supabase/functions/_shared/device.ts:17-26`, `src/features/auth/session.ts:69-79`, `src/lib/api.ts:61-71`

**Issue:** `device_fp` = SHA-256(User-Agent) minted at login, while the client sends SHA-256(`navigator.userAgent`). Chrome/Firefox embed the major version in both strings, so an automatic browser update *mid-session* changes the hash. Because the session is 7 days (`SESSION_SECONDS`), any officer whose browser updates during the week hits `device_mismatch` on their next lineup write — and `restFetch` then destroys the session (WR-06). UA-overriding extensions and corporate proxies that rewrite `User-Agent` produce the same permanent failure: the claim can never be re-matched until re-login, and re-login re-mints from the *new* UA, so a proxy that rewrites per-request leaves the officer unable to write at all. This phase is the first to route real work through the guard, so the exposure is new even though the mechanism is not.

**Fix:** if the guard stays, at least do not make it fatal for the session — see WR-06 — and prefer a stable input (e.g. a random per-device id persisted in localStorage and stored hashed server-side) over a value the browser mutates on update.

### WR-06: `clearSession()` on `device_mismatch` does not log the user out — it leaves a broken shell

**Severity:** WARNING
**File:** `src/lib/api.ts:77-89` (context: `src/features/auth/RequireAuth.tsx:62-80`)

**Issue:** On a `device_mismatch` body the client calls `clearSession()` (localStorage only) and throws `ApiError(401, 'unauthorized', 'device_mismatch')`. The comment claims "the user is bounced to login with the existing session-expired copy". Nothing bounces them: `RequireAuth` holds the session in React state and only reads localStorage in its `useState` initializer, so the authenticated shell keeps rendering with a dead token while every subsequent call fails. The user sees the "sua sessão expirou" copy but stays on a page where nothing works, with no path back to login except a manual reload.

**Fix:** give `api.ts` a way to invalidate the live session (an exported `onSessionInvalid` callback that `RequireAuth` registers, calling its `invalidate()`), or have `restFetch` throw a distinct error kind and let the page/`RequireAuth` handle the transition. At minimum, correct the comment so it does not describe behaviour that does not exist.

### WR-07: `lineupErrorCopy` shows "could not save" for read failures and for expired sessions

**Severity:** WARNING
**File:** `src/features/lineup/lineupModel.ts:166-185`, `src/features/lineup/LineupPage.tsx:74, 87`

**Issue:** One mapper serves both the initial **read** and every **write**. Only `device_mismatch` maps to `SESSION_ERROR`; a 401 from an expired token arrives as `ApiError(401, 'unauthorized', 'HTTP 401: …')`, which falls through every branch and lands on `GENERIC_ERROR = 'Não foi possível salvar a alteração. Tente novamente.'` So a member whose session expired sees "could not save the change" on a page that never saved anything, and has no hint that re-login is required. Any unrecognised read failure (500, malformed payload → `ApiError(0,'server')`) gets the same misleading copy.

**Fix:** pass the operation to the mapper and treat `unauthorized` as a session problem:

```ts
export function lineupErrorCopy(err: unknown, op: 'read' | 'write' = 'write'): string {
  const message = err instanceof Error ? err.message : ''
  if (message.includes('device_mismatch')) return SESSION_ERROR
  if (err instanceof ApiError && err.kind === 'unauthorized') return SESSION_ERROR
  if (message.includes('forbidden')) return 'Você não tem permissão para alterar a lineup.'
  ...
  if (op === 'read') return 'Não foi possível carregar a lineup. Tente novamente.'
  return GENERIC_ERROR
}
```

### WR-08: `0042`/`0043` hard-fail on live mutable state, and `0043` picks the "newest" identity non-deterministically

**Severity:** WARNING
**File:** `supabase/migrations/0042_battlefield_slader_alias.sql:111-123`, `supabase/migrations/0043_slader_identity_correction.sql:84-107` (and `:52-57`)

**Issue:** Both migrations re-assert the 0040 seed contract — `v_slots <> 80 or v_empty <> 0` raises. That contract is *not* invariant: the shipped UI has a "Limpar slot" button (`LineupPage.tsx:454-461`) and D-03 explicitly allows empty slots ("When the guild has < 80 active players"). `0043` additionally asserts the newest identity row is `Slader / 172453`, which any later validated submission changes. Because `apply-seed.mjs` has no applied-version gate, re-running either file after a normal day of use aborts on data the application considers valid — and `0042` is the file a future maintainer would reach for to re-apply the alias fix.

Second, `0043:52-57` and `:95-99` order by `created_at desc` **without** the `id desc` tiebreak that every display surface uses (`0014:170/191/648`, `0040:114`). Two identity rows written in the same transaction share `created_at` (the column defaults to `now()`, which is transaction time), so "newest" is arbitrary there: the idempotency check can append a duplicate `source='correction'` row, and the invariant block can fail on a tie.

**Fix:** make the invariants conditional (`if v_slots > 80 or v_parties <> 16`; drop `v_empty <> 0` once officers can legitimately clear slots) and add `, h.id desc` to both `order by` clauses in `0043`.

### WR-09: `0043` reproduces `correct_identity()` but skips its `assert_char_id_available` guard

**Severity:** WARNING
**File:** `supabase/migrations/0043_slader_identity_correction.sql:59-71` (context: `0014_whitelist_requests_identity.sql:200-244`)

**Issue:** The header says the migration "reproduces exactly what `public.correct_identity()` does". It does not: `correct_identity` calls `public.assert_char_id_available(v_char_id, p_member, null)`, which rejects a char id held by another member, another **pending membership request**, or another member's **pending submission**. `0043` only checks `members.char_id` and `member_identity_history.char_id`. It also attributes the row to "the oldest active owner" (`:46-50`) rather than the acting caller, and would insert `created_by = NULL` if no active owner exists (column is nullable, so it fails silently rather than loudly).

**Fix:** call the real guard (`perform public.assert_char_id_available('172453', v_member, null);`) and raise when `v_owner is null` instead of writing an unattributed history row.

## Info

### IN-01: Members receive the entire 131-row assignable roster, not just the lineup

**File:** `supabase/migrations/0040_battlefield_lineups.sql:168-179`

`get_lineups()` returns `roster` (every active, non-fixture member: `member_id`, `display_name`, `char_class`, `char_function`) to every caller, but only officers use it (the picker). Members therefore get a full member directory with classes — a wider surface than "your party and the two battlefields" from D-01, and the first place a plain member can enumerate the whole guild's class composition. Consider returning `roster` only when the caller is staff, or adding a `p_include_roster` flag defaulted false and used by `fetchLineups` only for staff.

### IN-02: Fixture names are hardcoded into production SQL, and the filter is bypassable

**File:** `supabase/migrations/0040_battlefield_lineups.sql:118-119, 241-242, 485-486`

`discord_handle not ilike 'smoke%' / 'dummy-%'` lives in `get_lineups`, `set_lineup_slot` and the seed invariant. A real member whose handle begins with "smoke" can never be seated, and the filter is cosmetic anyway: `authenticated` still holds SELECT on both tables (`0040:62`), so fixtures are only hidden from the RPC, not from the data. Prefer a `members.is_fixture boolean` column (or a dedicated schema) over name prefixes, and rely on RLS rather than string filters for visibility.

### IN-03: Dead payload field and unused exports

**File:** `src/lib/api.ts:1535`, `src/features/lineup/lineupModel.ts:155-164`, `src/features/lineup/lineupExport.ts:163-171, 266-268`

`LineupParty.filled` is validated and typed but never read — both the grid and the exporter recompute the count from `slots` (`partyFilledCount`), so a server/client disagreement (e.g. WR-01's ghost slot) is silently resolved in the client's favour. `slotAt()` and `lineupFilename()` are exported but referenced only from tests. `buildColumn` also creates a `filled: 0` object and then mutates `normalized.filled = filled`; pass the count in the literal instead.

### IN-04: `char_function` is cast, not validated, in the closed-payload narrowers

**File:** `src/lib/api.ts:1574, 1628`

`asLineupSlot` validates `slot_index`/`member_id`/`display_name`/`char_class` and then does `(value.char_function ?? null) as LineupSlot['char_function']`; the roster narrower does the same. Every other field is checked, so this is the one place an arbitrary server string can enter a union type. No leak (the returned object is closed) and no current consumer reads it, but the type is lying. Validate against `['dps','mdps','suporte']` like the other payloads do.

### IN-05: The role-label editor discards the officer's text on a failed save; tablist contains a non-tab

**File:** `src/features/lineup/LineupPage.tsx:572-585, 174-207`

`onSave(...)` is followed immediately by `setEditing(false)`, so if the save fails (device_mismatch, forbidden, network) the editor closes and the typed label is lost while the error appears at the top of the page — the officer has to retype it. Keep the editor open until the mutation resolves. Separately, the "Ver ambas" toggle (`:199-206`) sits inside `role="tablist"` without `role="tab"`, which is an ARIA structural violation.

### IN-06: The smoke battery mutates the live lineup and can leave it empty

**File:** `scripts/smoke-lineup.mjs:127-142, 144-147, 78`

`restore()` first nulls **every** slot (`update lineup_slots set member_id = null where true;`) and then re-seats 80 rows. That is only safe if the Management API runs the whole multi-statement string as one implicit transaction; nothing in the script enforces `begin`/`commit`, and a mid-string failure leaves the guild's lineup empty. It also clobbers any concurrent officer edit made between `snapshot()` and `restore()` (the comparison then "passes" against the stale snapshot). `cleanupFixtures()` deletes member rows by handle, but `member_identity_history.member_id` has no `ON DELETE CASCADE` (`0014:71-82`), so one stray identity/proof row makes the delete fail and leaves a fixture that breaks the next run's insert. Add explicit `begin; … commit;` to the restore query, scope it to the rows actually touched, and delete dependants before the member rows.

### IN-07: Nothing asserts the new members' generated `login_key` is unique

**File:** `supabase/migrations/0040_battlefield_lineups.sql:372-417` (context: `0020_first_access_by_nickname.sql:29-33`, `0040:118-119`)

The 39 inserts are guarded only on `lower(discord_handle)`. `members.login_key` is `generated always as (lower(btrim(display_name))) stored` with a plain (non-unique) index, and `first_access_claim` raises `ambiguous_identity` when two active rows share a `login_key`. A display-name collision between a new row and an existing member would therefore silently make *both* accounts unclaimable — the exact opposite of D-02's goal. Add an invariant to the seed block: `raise` when any `login_key` among active members has `count(*) > 1`. Related doc drift: `device.ts:10-12` still says the claim is minted "at first access (setup-pin)", a function retired by 0034.
