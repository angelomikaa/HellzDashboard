## Blocker (requires owner decision)

`public.assert_device_bound()` and `public.request_device_fingerprint()` do **not** exist in the live database. Migration `0024_device_binding_enforcement.sql` (plan 08.1-08, SEC-04) was never applied live. The live `schema_migrations` row `0024` is a different migration (`role_rank_role_filter`), and none of the live staff RPCs (`set_member_role`, `set_member_active`, `reset_member_pin`, `add_member`) call the guard.

Effect on this plan: `set_lineup_slot` and `set_lineup_party_label` run the guard first and raise SQLSTATE 42883, so every officer write fails closed (PostgREST returns 404). No unauthorized write is possible, but no officer can edit a lineup until the guard exists. The read path and the RLS denial are unaffected.

**Hazard:** `0024_device_binding_enforcement.sql` in the repo is a stub. Its four `set_*`/`add_member`/`reset_member_pin` bodies contain only the guard plus a comment, so applying it as written would blank those live function bodies. It must not be applied as-is.

**Decision needed:** install the device guard as a new append-only migration (`request_device_fingerprint` / `assert_device_bound` with the 0024 definitions), and decide whether to enforce it on the existing staff RPCs in the same change. Alternatively, the lineup RPCs could drop the guard, but that contradicts CONTEXT D-01 and AGENTS.md, so I did not choose that.
