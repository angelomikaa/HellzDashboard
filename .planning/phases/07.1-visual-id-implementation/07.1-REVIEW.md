## Warnings

### WR-01: `animate-pulse` violates the D-05 static-only invariant, and the reduced-motion kill-switch does not cover animations

**File:** `src/features/submit/StatGroupStep.tsx:113`, `src/features/submit/SubmitPage.tsx:428`, `src/index.css:246-250`
**Issue:** The D-17 "skeleton" reading state applies Tailwind's `animate-pulse`, which injects an `@keyframes pulse` animation — the phase invariant explicitly states "static-only neon (no @keyframes/animation — hover/focus transitions are permitted per D-05)". Compounding this, the global `prefers-reduced-motion` kill-switch in `index.css` only forces `transition: none !important` — it does not disable `animation`, so reduce-motion users still get the pulsing inputs.
**Fix:** Either drop the pulse (the `Lendo captura…` placeholder + `disabled` already signal the state), or make the reduced-motion rule complete and scope the animation explicitly:

```css
@media (prefers-reduced-motion: reduce) {
  *, ::before, ::after {
    transition: none !important;
    animation: none !important;
  }
}
```

and replace `animate-pulse` in both call sites with a static reading style (e.g. `opacity-60`), or a custom `@utility` that is D-05-annotated.

### WR-02: Destaques uses non-unique `display_name` as React key — same hazard the codebase already fixed in KeyStatsPage

**File:** `src/features/highlights/HighlightsPage.tsx:105`
**Issue:** `<PromotionCard key={card.display_name} ...>` — `display_name` has NO unique constraint (migration 0001; documented verbatim in `KeyStatsPage.tsx:280-287`: "two same-class members can share a nickname, so a name-only React key can collide and drop rows"). Two Impecável players with the same nickname in one class produce duplicate keys → React reconciliation can drop or mis-render a card. The composite-key fix was applied to the class_top5 list but not here.
**Fix:** Compose the key from stable per-card data, e.g.:

```tsx
<PromotionCard
  key={`${card.display_name}-${index}`}
  card={card}
  charClass={section.class_name}
/>
```

(preferred long-term: return member id from `get_promotion`, as noted in the KeyStatsPage comment).

### WR-03: Percentual inputs in the submit wizard have no left padding — text renders flush against the border

**File:** `src/features/submit/StatGroupStep.tsx:113`
**Issue:** `${percentual ? 'pr-8' : 'px-3'}` — percentual fields get only `pr-8` (right padding for the `%` suffix) and lose the left padding entirely, so typed/OCR-prefilled values start hard against the left border. In a visual-identity phase this is a visible defect on every percentual row (Quasi/Especial steps).
**Fix:**

```tsx
${percentual ? 'pl-3 pr-8' : 'px-3'}
```

### WR-04: Login lockout state never clears client-side — recovery requires a manual page reload

**File:** `src/features/auth/LoginPage.tsx:24,91-99`
**Issue:** On 429 the form enters `kind: 'locked'`, which disables both inputs and the submit button (`disabled = submitting || locked`) with no timer or retry affordance. The lockout is server-enforced and expires, but the client stays hard-locked forever — a player who waits out the window must reload the page to try again, with no on-screen indication of that.
**Fix:** After rendering the locked message, schedule an unlock when `retry_after_seconds` elapses:

```tsx
useEffect(() => {
  if (status.kind !== 'locked' || unlockAt === null) return
  const t = setTimeout(() => setStatus({ kind: 'idle' }), unlockAt - Date.now())
  return () => clearTimeout(t)
}, [status, unlockAt])
```

(storing `unlockAt = Date.now() + retry_after_seconds * 1000` at 429 time), or at minimum add a "Tentar novamente" affordance that resets to `idle` so the next attempt re-engages the server check.

## Info

### IN-01: ConfirmDialog Shift+Tab from the confirm button is a no-op

**File:** `src/features/admin/ConfirmDialog.tsx:68-70`
**Issue:** The focus-trap handler maps Shift+Tab on *either* button to `confirmRef.focus()` — so Shift+Tab on Confirm keeps focus on Confirm instead of cycling to Cancel. Focus remains trapped (no escape), but the reverse cycle is broken.
**Fix:** For `e.shiftKey && active === confirmRef.current`, focus `cancelRef.current`.

### IN-02: CropOverlay modal has no focus trap

**File:** `src/features/submit/CropOverlay.tsx:217-273`
**Issue:** Unlike `ConfirmDialog` (which implements a two-button trap), the crop dialog only focuses the confirm button on open and handles Escape. Tab cycles out of the overlay to the underlying wizard controls, which are visually hidden behind `bg-black/80` but still keyboard-operable while the modal is open. Inconsistent with the shared modal's stated a11y contract.
**Fix:** Apply the same Tab-wrap pattern as `ConfirmDialog` (two focusables: Cancelar / Usar recorte).

### IN-03: Dead focus-ring classes on the step-verification label

**File:** `src/features/submit/SubmitPage.tsx:89`
**Issue:** `focus-within:focus-visible:ring-2` compiles to a selector requiring the `<label>` itself to match `:focus-visible` — a non-focusable element never does, so the rule never renders. (The inner `checkbox-brand` input carries its own `focus-visible:ring-2 ring-accent`, so a focus indicator still exists; the label classes are dead code.)
**Fix:** Drop `focus-within:focus-visible:ring-2 focus-within:focus-visible:ring-accent` from the label, or switch the intended effect to `has-focus-visible:ring-2` (Tailwind v4 `has-*` variant) if a row-level ring is wanted.

### IN-04: CollapsibleGroup chevron uses `transition-transform` — a transform state transition under D-05's letter

**File:** `src/features/dashboard/CollapsibleGroup.tsx:45`
**Issue:** `index.css`'s own D-05 commentary states "no transforms, no keyframes" for hover/motion feedback; the chevron's `transition-transform` + `rotate-90` is a transform transition on a *state* change (neither hover nor focus). Impact is minimal (the global kill-switch covers `transition`, so reduce users get instant rotation), but it is a letter-of-invariant inconsistency worth a deliberate decision.
**Fix:** Remove `transition-transform` for strict static compliance, or document an explicit ratified exception next to the D-05 block in `index.css`.

### IN-05: `ROLE_LABELS` duplicated between App shell and Personagens

**File:** `src/App.tsx:12-16`, `src/features/admin/CharactersPage.tsx:48-52`
**Issue:** Identical `Record<'member' | 'officer' | 'owner', string>` label maps defined in two files — a drift risk if a role label changes.
**Fix:** Move to `src/lib/groups.ts` (already the shared label home for `FUNCTION_LABELS`) and import in both.

### IN-06: Byte-identical brand SVG duplicated as favicon and imported asset

**File:** `public/favicon.svg`, `src/assets/hellz-mark.svg`
**Issue:** The two files are identical copies of the same logo. Any future brand tweak must be applied twice or the favicon and header mark diverge.
**Fix:** Acceptable as-is for cache-isolation reasons (favicon must live in `public/`); if kept, add a comment in each noting the twin's path, or generate one from the other at build time.

### IN-07: 429 without `retry_after_seconds` renders the "cannot connect" copy

**File:** `src/features/auth/LoginPage.tsx:91-101`
**Issue:** A 429 whose body lacks a numeric `retry_after_seconds` (gateway-level rate limit before the function runs) falls through to `NETWORK_ERROR` — "Não foi possível conectar ao servidor…" — which is misleading (the server was reached and rate-limited the client). The copy remains enumeration-safe, so impact is copy accuracy only.
**Fix:** Add a final branch mapping any 429 (with or without the field) to a generic "Muitas tentativas. Tente novamente mais tarde." line.
