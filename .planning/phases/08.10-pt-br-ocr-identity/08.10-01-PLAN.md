# 08.10-01 — pt-BR OCR identity hotfix

## Problem (observed 2026-10-22, owner UAT)

First access is blocked with "Não conseguimos ler o ID, o nick e a classe" for a valid
Básico print. Root cause: the identity parser was written against the English client
fixture (`public/examples/basic.png`: `Job Gypsy`) while the live client is pt-BR
(`Classe Criador`).

- `JOB_PATTERN` never matches `Classe`, so `char_class` is always null.
- `matchClassName('Criador')` returns null: `OFFICIAL_CLASSES` is English-only and
  `setup-pin` validates against the English `classes` catalog.
- `parseBasicProfileText` rejects any digit-bearing line, so a merged SPARSE_TEXT
  line (nickname + class + ID) also loses the nickname.

## Tasks

1. **identity.ts — class scan + aliases.** Replace the single `Job` regex with a
   label alternation (`Job|Class|Classe|Clase`), iterate every occurrence and keep
   the first value that resolves through `matchClassName`. Add a diacritic-folding
   `normalizeClassName` and a `CLASS_ALIASES` table (pt-BR/es base + trans names)
   mapping to the 15 official English names. Exact alias match is evaluated before
   English containment so `Mestre` -> `Champion` is not shadowed by `Mestre-Ferreiro`.
2. **identity.ts — nickname.** Prefer the band left of the class label on the same
   line (positional evidence, digits allowed there); fall back to the existing
   standalone-line rule. Add localized keywords (guilda, líder, classe, poder, nv).
3. **recognize.ts — whitelist accents** so localized names/nicknames are not mangled.
4. **firstAccess.ts + FirstAccessPage.tsx** — `profileProblemMessage(profile)` names
   the missing field(s) (`a classe`, `o ID`, `o nick`); `PROFILE_ERROR` stays the
   all-null copy.
5. **Tests** — pt-BR merged/separate lines, job-level row shadowing, alias mapping
   invariants, unchanged English behaviour, field-specific copy.
