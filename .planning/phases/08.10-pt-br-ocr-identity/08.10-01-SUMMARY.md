# 08.10-01 SUMMARY — pt-BR OCR identity hotfix

## What was broken

Owner UAT (2026-10-22): first access on the live client was blocked with
"Não conseguimos ler o ID, o nick e a classe. Envie outro print." for a perfectly
readable Básico print.

Root cause was a **locale mismatch**, reproduced at the parser level with the exact
text from the report:

```
SoldierHelIz / Classe Criador / ID 17069 / Líder da Guilda Suprema / Poder 318038
  before -> {nickname: SoldierHelIz, char_id: 17069, char_class: null}
  after  -> {nickname: SoldierHelIz, char_id: 17069, char_class: Biochemist}
```

1. `JOB_PATTERN` only matched the English label `Job`; the live client prints
   `Classe` (pt-BR) / `Clase` (es), so the class was never even looked at.
2. `matchClassName('Criador')` returned `null`: `OFFICIAL_CLASSES` and the
   `classes` catalog are English (`Biochemist`), and there was no alias table.
3. A digit-bearing line was never accepted as a nickname, so a merged SPARSE_TEXT
   row (`SoldierHelIz Classe Criador ID 17069`) also lost the nickname.
4. The retry copy claimed all three fields failed even when only the class was
   unreadable.

## What changed

| File | Change |
|------|--------|
| `src/features/submit/identity.ts` | Label-alternation class scan (`Job/Class/Classe/Clase`) that tries **every** occurrence and keeps the first that resolves; `CLASS_ALIASES` (pt-BR/es base + trans names) with exact → longest-containment → bounded-Levenshtein matching; diacritic-folding normalization; nickname chosen from the band **left of** the class label or the band **adjacent above** it, with standalone lines as the last resort; ID label accepts the measured `1D`/`lD` misreads |
| `src/features/submit/ocr/recognize.ts` | Identity whitelist widened with accented Latin letters; dev-only `console.debug` of the raw identity text (a rejected claim was previously undiagnosable) |
| `src/features/auth/firstAccess.ts` | `profileProblemMessage(profile)` names the missing field(s); `PROFILE_ERROR` stays the all-null copy |
| `src/features/auth/FirstAccessPage.tsx` | Renders the field-specific copy |

## Verification

- Unit: 31 identity tests (was 18) — localized aliases, alias→catalog invariant,
  pt-BR merged/separate bands, job-level `Classe Nv40` row cannot shadow the class,
  tab labels/artifacts above the nickname band, Spanish label, `1D`/`lD` ID label.
- Seam: `recognize.profile.test.ts` parses the live pt-BR text end to end.
- Copy: field-specific retry message tests in `FirstAccessPage.test.tsx`.
- Real OCR run (node Tesseract, same PSM/whitelist as production):
  - synthetic pt-BR Básico header → `SoldierHellz / 17069 / Biochemist` (the
    double-l is the synthetic Arial render, not a parser issue);
  - shipped English fixture `public/examples/basic.png` → `Ahrya / 32980 / Gypsy`;
  - **owner-seeded real pt-BR sample** (`.secrets/ocr-samples/Samplebasicptbr.png`,
    707x345): `Ahrya` / `1D 32980 E` / `Classe Sumo Sacerdote` →
    `{nickname:'Ahrya', char_id:'32980', char_class:'High Priest'}`, and the Basic
    pill read yields `298393` (combat_power) — the multi-word localized name and
    the `1D` misread both resolve on real pixels.
- The first real-sample run exposed a copy-icon artifact line (`SN`) sitting
  between the name and the class band and winning the nickname. The band window
  is now SCORED (lowercase / length / proximity) instead of nearest-wins; the
  measured text is pinned as a regression test.
- Full suite 547+ green, `tsc -b` clean, `npm run build` green, oxlint unchanged
  (pre-existing `RankPage` fast-refresh warnings only).

## Decisions

- **Localized base names map to the catalog's transcendent entry** (`Cavaleiro` →
  `Lord Knight`), mirroring the pre-existing English containment rule
  (`Assassin` → `Assassin Cross`) and the seed's rename table.
- **Digits are allowed only in the nickname band** (left of the class label, or the
  line immediately above it) — the game prints the nickname there, so `Helz2010`
  is recoverable; detached lines stay digit-free so stat rows are never names.
- **Containment needs ≥3 characters** so the `Nv` fragment of `Classe Nv40` can
  never resolve a class (`invocador` contains `nv`).
- **Unknown localized names still yield `null`** — never a guessed class (D-03).
  A new locale/spelling is added to `CLASS_ALIASES`.

## Follow-ups (not in this hotfix)

- The alias table covers the pt-BR trans/base names plus a few Spanish forms;
  add entries as new spellings appear (owner can confirm against the live client).
- Browser re-walk of first access on the live client is the acceptance step.

## Decisions

- **Both vocabularies are always tried.** A locale switch (or a mixed guild) must
  not require a config flag; the labels are disjoint enough that conflicts
  resolve on score, and a real row's exact match always beats a near match.
- **Ambiguous pt rows are left to order mode instead of guessed.** The four
  PvE/PvP quasi rows clip to `…ção de Dano J…` where the icon glyph lands, so no
  transcription is trustworthy; the 13+13 Avançados capture assigns by order.
- **Accents are folded, not required.** `PRECISAO` and `PRECISÃO` compare equal,
  so the whitelist widening cannot *break* a read that worked before.

# 08.10 (cont.) — the Especial panel omits zero rows

Owner clarification (2026-10-22): *"when the stat is 0, it does not show 0.00%, it
omits the line altogether, so in case a line is missing the default is 0, not
'failed to read'. failed to read is just in case it actually fails to read
altogether."* The new sample `sampespecialtdr.png` proves it both ways: `TdR
Global%` prints `-10.00%` here but had no line in the earlier sample (it was 0),
and `Dano x Bruto` / `Redução de Dano x Bruto` are missing here (they printed
`1.00%` / `2.00%` in the earlier one).

## What changed

- `GAME_LABELS_PT.global_cd_pct = 'TdR Global%'` (owner sample) and
  `GAME_LABELS_PT.max_hp_pct = 'PV Máx%'`. `max_hp_pct` is deliberately
  vocabulary-only: no capture reads it, but naming it keeps the `PV Máx%` row
  from counting as an unreadable row.
- `RowGrammar.omitsZeroRows` (set on `special`) + pure `omittedZeroKeys()` /
  `OMITTED_ZERO_RAW`: a key with **no row, between two rows we did read**, is
  filled as `0`.
- `readRowsScreen` classifies each rendered row as *matched*, *known elsewhere*
  (a stat from another section that scrolled into frame — matched against the
  full label universe at ≥ 85), or *unexplained*. Any unexplained row, or two
  rows claiming one key, disables the zero inference for that screenshot.

## Why the edges are NOT zeroed

The rule only applies **between** the first and last row that was read. A
cropped or scrolled shot (`samppt1.png`) that is cut off mid-section would
otherwise fill 0 for every row below the fold — the exact opposite of "failed to
read". Those edge keys stay `failed`, which is what the player must fix.

## Measured (production pipeline)

| Capture | Result |
|---------|--------|
| `sampidealptidealespecial.png` (TdR Global% absent) | 15/15 — `global_cd_pct` = **0** |
| `sampespecialtdr.png` (TdR Global% = -10.00%, both Bruto rows absent) | 15/15 — both Bruto keys = **0** |
| Comuns / Avançados / English canonical / G / H / F | unchanged, green |

Harness `I` pins 4 localized Details captures = 70 outcomes, all 70 exact.
Full suite green; the two pt-BR tooltip samples are pinned separately in `J`

**Regression the harness caught:** the first cut of the "known elsewhere"

preference now requires ≥ 85 (exact/containment) — the same idea as the
short-label fix above: a fuzzy match may never outrank a real vocabulary match.

## Tooltips (raw defenses) in pt-BR — Phase 9.1's flow, not the first input

Phase 9.1 reads raw defenses from **tooltip** captures on their own screenshot
basis (`.secrets` `samplepdef.png` / `samplemdef.png`, plus the pt-BR
counterparts) — they are not part of the first-input Details steps, so they are
pinned in their own harness list (`J`), never mixed into the Details experiment
(`I`).

The owner-seeded pt-BR tooltip line is **`DEFF de Equipamento: 5149`** /
**`DEFM de Equipamento: 1525`**. The 9.1 reader required the literal English word
`equipment`, so both reads failed on the live client. `TooltipGrammar.labelPt`
now carries the localized wording and the guard accepts `equipment` **or**
`equipamento` (still rejecting `Base PDEF`, the description line, and `DEFF
obtido de equipamentos…`). Harness `J` pins both: 5149 / 1525 exact.

### Only the EQUIPMENT line is read (owner-clarified)

The tooltip prints **two** numbers, measured band by band on the 9.1 basis:

| Capture | base line | equipment line | read |
|---------|-----------|----------------|------|
| `samplepdef.png` | `Base PDEF: 136` | `Equipment PDEF: 4760` | **4760** |
| `samplemdef.png` | `Base MDEF: 228` | `Equipment MDEF: 1523` | **1523** |
| `samplepdefpt.png` | `Base PDEF: 117` | `DEFF de Equipamento: 5149` | **5149** |
| `samplemdefpt.png` | `Base MDEF: 263` | `DEFM de Equipamento: 1525` | **1525** |

Per the owner: *"the values will vary according to the character, what matters
is that base def + equipment def = pdef, and we want equipment def specifically
for the equation."* So the rule lives in `isTooltipLabelLine()` and looks at the
**wording only, never at the numbers** — the base line has no
`equipment`/`equipamento` in it, so it can never be selected, and the value being
136 or 5149 changes nothing. `rawDefense.ts` then uses exactly that term:
`rpdef = floor(equipment / (1 + equip_pdef_pct/100))`, with the pct coming from
the Especial column (the one capture where `ATQF/ATQM/DEFF/DEFM de
Equipamento%` are read). Unit tests cover the real OCR deformations
(`Equipment PDEFO`, `Base PDEFé`) and the itemized description line.

# 08.10 (cont.) — the nickname is anchored on the card layout

Owner report (2026-10-22): a real capture prefilled **"dh"** as the nickname.
Reproduced with `.secrets/ocr-samples/sampidentityaryah.jpg` (725x341): the full
frame already read `Aryah`, but any crop that starts inside the name left only a
fragment — `ryah`, `yah Vd`, `ah`, `Arvah /` — and the text parser took the
fragment as a name. An intact card crop also split the name into two words
(`"A"@169,26,188,48` + `"ryah"@190,25,245,56`), degrading `Aryah` to `ryah`.

## What changed

| File | Change |
|------|--------|
| `identity.ts` | `nicknameFromLayout(words, imageWidth)` — the nickname is the word **left-aligned with the class label** in the band one text line above it (measured 169 vs 170 px on the reported shot; 158/157 English; 167/168 pt-BR), split fragments glued back (`A`+`ryah` → `Aryah`), the pencil/copy badge dropped (printed smaller and apart: 14 px vs the name's 31 px). No aligned word ⇒ `null`, never a fragment. |
| `identity.ts` (shape) | `nicknameCandidate` requires **≥ 3 letters**, letters/digits/spaces only, starting with a letter — `dh`, `oy`, `Pp`, `ah`, `y Arvah /` are no longer names. The unanchored fallback (no class band in frame) additionally requires a capitalised first letter, because a clipped name prints as a lowercase fragment (`ryah`, `yah Vd`). |
| `recognize.ts` | `readBasicProfile` requests `blocks` and feeds the word boxes to the layout; when a class band IS in the capture the layout owns the nickname (`null` = not readable), otherwise the (now stricter) text heuristics run. |

Harness experiment `K` pins the three identity samples (nickname + ID + class)
and the clipped crop (`null`). Unit: 7 new `nicknameFromLayout` cases built from
the measured word boxes plus the fragment-shape rejections; identity suite 38
green.

## Decisions

- **Layout beats text when the card header is visible.** A short line can be a
  name or a fragment; only geometry tells them apart — the class label's left
  edge is the card's text column, and the game prints the name on it (1 px on
  every sample measured).
- **Empty is the correct answer for a cut name.** The player types it (D-03:
  never guess an identity); prefilling `dh` is worse than prefilling nothing.
- **The badge is excluded by size, not by position.** The edit-pencil/copy icon
  prints at roughly half the name's glyph height, so it can never be glued into
  the name even when SPARSE_TEXT puts it on the same line (`SN`, `MA`, `2`).

## Comprovante path — capture parity (2026-10-22)

Second owner report on the same `dh`: the live distortion is on **solicitar
acesso > identificação > usuário do discord > Comprovante (print do personagem,
JPEG)**, and that field must accept the same optimal capture as the stats and
recruiting flows.

The proof field was the last plain file input: it decoded the upload, downscaled
it to **≤1600 px**, ran `readBasicProfile` on that downscaled copy and had no
aspect gate and no crop. The wizard, by contrast, reads the NATIVE image and
isolates the panel with `CropOverlay`. On a phone screenshot the two differ by a
factor of 2-4× on the card header, and a **dark game backdrop is not thresholded
at all** (measured: the same card inside a 1080x2400 dark frame reads *nothing* —
`raw=""` — while the identical composite on a light backdrop reads the full card,
`Aryah`/`Classe Sumo Sacerdote`/`ID 399432`).

`ProofField` now mirrors the wizard end to end: `/examples/basic.png` + hint,
`needsCrop(aspect, CAPTURES.basic.aspect)` gate (>5%, owner-ratified threshold),
the same `CropOverlay` (full-image default box, always-confirm), the identity OCR
on the **native/cropped** canvas, and only the upload copy downscaled to
≤1600 px / JPEG 0.85. The decode is shared (`decodeUpload`), so EXIF orientation
and the fallback chain are identical too.
