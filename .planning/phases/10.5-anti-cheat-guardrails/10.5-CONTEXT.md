# Phase 10.5 — Anti-Cheat Guardrails (CONTEXT)

**Owner request (2026-10-30):** "we need to increase safety against cheating — the form is supposed to be filled with no buffs, but some players might try to bypass it in order to get better ranking. The main stats to look for are base DEF in the Equipment PDEF print, and the equipment pdef%. Buffs like Angelus and assumptio will increase these stats by almost 100%, so any input that nearly doubles the guild average for these stats must be flagged. Also, fields that are altered by the user after reading must be tracked, and we also need warnings for high fluctuation in OVR without class or role change, to start."

## Locked decisions (owner, 2026-10-30)

| # | Decision |
|---|----------|
| D-10.5-01 | Baseline = the **same class + build-role cohort**, not the whole guild. Latest validated value per active member, submitting member excluded, **n ≥ 3** (the same data-sufficiency gate every rank surface uses). |
| D-10.5-02 | Spike threshold = **≥ 1.5×** the cohort average. Watched stats: `rpdef`, `rmdef`, `equip_pdef_pct`, `equip_mdef_pct` (Angelus inflates Base PDEF ~95%; Assumptio inflates Equipment PDEF/MDEF ~95%). |
| D-10.5-03 | A tripped submission is **saved pending, never blocked**, and the officer's Validações card shows the warnings. Legitimate outliers (new gear) must remain submittable; the officer owns the decision. |
| D-10.5-04 | OVR swing warning = **≥ 8 points** between the current validated OVR and the projected OVR, **only when class and build-role are unchanged**. |
| D-10.5-05 | OCR edit tracking stores, per input: `source` (`ocr` / `ocr_edited`), the value the OCR printed, and the final submitted value. Equipment tooltip inputs (`equip_pdef_raw` / `equip_mdef_raw`) are included (RPDEF/RMDEF derive from them). |

## Non-negotiables

- **Server-side detection.** The client warning is advisory; `officer_queue()` returns the authoritative flags. No rank math moves to the browser.
- **One formula.** The projected OVR uses the Phase 9 / 10.1 value-proportional expression copied from the live `role_rank` body (0036); never re-derived.
- **Append-only.** `submission_provenance` is a new append-only table; `submission_stats` is untouched. `create_submission` v4 keeps every 0014 validation and adds the optional provenance array.
- **No key-stat leak.** Neither the baselines RPC nor the flags payload exposes key-stat config.
- **No new npm dependencies.**
- **RLS.** `submission_provenance` is RLS-on with no policies; only the definer surfaces read/write it.

## Out of scope (first slice)

- Automatic rejection or hold of suspicious submissions.
- Detecting buffs on stats other than the four defense values (the owner named these as the main ones).
- Historical trend charts / per-member cheat scoring.
- Screenshot retention (screenshots still never leave the device).
