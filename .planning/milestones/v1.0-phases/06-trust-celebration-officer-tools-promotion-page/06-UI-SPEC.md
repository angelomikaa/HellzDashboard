# Phase 6 — UI Design Contract

> Visual and interaction contract for Phase 6 (Validações staff tab, Destaques promotion page, Personagens owner controls, HistoryList status label). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Source of decisions:** 06-CONTEXT.md D-01..D-14 (locked), 06-RESEARCH.md (verified repo patterns), 01-UI-SPEC/04-UI-SPEC (established visual language). ## Design System

| Property | Value |
|----------|-------|
| Tool | none (manual Tailwind CSS v4 + `@theme` tokens in `src/index.css`) |
| Preset | not applicable |
| Component library | none — hand-rolled leaf components per the established house pattern (OvrHero/StatCard precedent) |
| Icon library | none (text-only UI today — Phase 6 introduces no icons) |
| Font | system UI stack (unchanged; no webfont) |

**Hard constraints carried forward:**

- Tier styling flows ONLY through the literal maps `TIER_BORDER`/`TIER_TEXT`/`TIER_BG` from `src/features/dashboard/presentation.ts` (Tailwind v4 JIT never sees interpolated class names). New promotion-card components MUST consume these maps, never build new tier CSS or tokens.
- OVR banding via `tierForOvr` (presentation.ts:19–25); highlight-facet banding via `tierForPoints` (10–16). Never re-declare band constants.
- Values rendered via `formatStatValue` (`src/lib/parseStatValue`) for FLAT/PERCENTUAL parity with the dashboard.
- Guards are UX-only; enforcement is server-side (RLS/RPC). Every staff surface assumes a tampered client.
- Group labels Geral/Quasi/Especial from `src/lib/groups.ts` (`GROUP_LABELS`); function badges from `FUNCTION_LABELS` (DPS/Tank). No new label sources.
- Role labels from the existing `ROLE_LABELS` maps (Membro/Oficial/Proprietário).
- RNK-02: promotion cards NEVER render any "key stat" flag, ordering hint, or label. The 6 highlights are presented as plain "melhores stats" — no wording may imply key-stat identity.

## Typography

Existing project scale — exactly these sizes and weights, no additions:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / values | 16px (`text-base`) | 400 | 1.5 |
| Label / secondary | 14px (`text-sm`) | 400 (muted lines) / 600 (`font-semibold` labels) | 1.5 |
| Heading | 20px (`text-xl`) | 600 (`font-semibold`) | 1.2 |
| Display (OVR number on cards) | 48px (`text-5xl`) | 600 (`font-semibold`) | 1.0 (`leading-none`, OvrHero precedent) |

Rules:

- Exactly 2 weights in use: 400 regular, 600 semibold. No bold (700), no light.
- The promotion card's OVR uses the Display role (text-5xl, tier-colored via `TIER_TEXT[tierForOvr(rounded)]`) — the OvrHero composition is the literal precedent (`border-2` + tier text on `bg-surface p-6`).
- Stat labels inside cards/facets: 14px semibold `text-content`; value-type tag (FLAT/PERCENTUAL): 14px `text-muted` — StatCard anatomy (StatCard.tsx:47–52).

## Interaction Contracts

### Surface 1 — Validações staff tab (AUTH-05; D-03/D-04/D-05/D-06)

**File home:** `src/features/admin/ValidacoesPage.tsx`; tab `'validacoes'` in App.tsx `Tab` union; nav button wrapped in `{isStaff && ...}` (exact CharactersPage/Stats-Chave pattern); content re-check `showValidacoes = tab === 'validacoes' && isStaff` (UX-only gate; enforcement is the `officer_queue()` RPC staff gate).

**Data:** `fetchOfficerQueue(session)` — one RPC call on mount; refetch after every action. Rows newest-first by `submitted_at` (server-ordered). The 0010 one-pending rule means at most one row per member — list is naturally deduplicated. No pagination.

**List item (collapsed):**

- Full-width row: `rounded-md border border-line bg-surface px-3`, `min-h-11`, tap anywhere to expand (the whole row is the toggle button — `aria-expanded` on it).
- Content: **player display name** (16px, text-content), meta line (14px, text-muted): `{char_class ?? '—'} · {FUNCTION_LABELS[char_function]} · {dateTimeFormatter.format(submitted_at)}` (pt-BR short date+time, HistoryList precedent).
- Chevron affordance: text-only `▸`/`▾` prefix (14px, text-muted) — no icon library. (auto-resolved)

**Expanded review (D-04 — all 57 values, read-only):**

- Three collapsible group sections in fixed order **Geral → Quasi → Especial** (`GROUP_ORDER`/`GROUP_LABELS` from `src/lib/groups.ts`), each headed 14px semibold, defaulting to **expanded** for Geral, collapsed for Quasi/Especial. (auto-resolved)
- Value rows use the StatCard visual vocabulary: label 14px semibold left, value right; value rendered via `formatStatValue` with the value-type context (`flat` → plain number, `percentual` → `%` per parseStatValue convention); value-type tag `FLAT`/`PERCENTUAL` 14px text-muted beside the label (StatCard.tsx:47–52 anatomy).
- **Read-only is absolute:** no inputs, no PATCH, no edit affordance anywhere. The word "editar" must not appear on this page.
- Actions bar pinned below the groups inside the expanded card: **Validar** (accent primary, `h-11 rounded-md bg-accent px-4 text-base font-semibold text-accent-foreground`) and **Rejeitar** (outline button, `h-11 rounded-md border border-line px-4 text-base font-semibold text-content` — NOT destructive-colored at rest; the destructive color appears in the confirm modal).
- Both actions open the modal confirm (copy table above) before the RPC. Buttons disabled while in-flight (`aria-busy`); a page-level `busy` pattern disables every action (CharactersPage precedent).
- On success: refetch queue (the row leaves — status no longer pending); show inline success line 14px `text-success`: `Envio validado.` / `Envio rejeitado.` (auto-resolved)
- Stale-queue race (two officers): on RPC error `not_pending`, show enumeration-safe `Este envio já foi avaliado por outro oficial.` and refetch the queue. (auto-resolved; maps to RESEARCH Pitfall 9)

**States:** loading `Carregando…`; empty `Nenhuma submissão aguardando validação.`; error = global enumeration-safe copy with the page still mounted.

### Surface 2 — Destaques promotion tab (SHWC-02; D-01/D-02/D-12/D-13/D-14)

**File home:** `src/features/highlights/HighlightsPage.tsx`; tab `'destaques'`; nav button rendered for EVERY role (no `isStaff` wrapper — mirrors `showSubmit`); no role gate, no content re-check needed beyond session existence. Enforcement is the member-invocable `get_promotion()` RPC.

**Data:** `fetchPromotion(session)` — one zero-argument RPC call on mount returning all class sections at once. Classes with insufficient data are omitted server-side (D-13); the client additionally renders the empty state when the array is empty.

**Page composition (D-13):**

- One section per class, order: server order (ovr-desc strength of the top card — stable; client does not reorder). Section heading: class name, 20px semibold text-content.
- Card grid inside each section: **1 column mobile → 2 columns ≥ sm → 3 columns ≥ lg** (DashboardPage 04-03 grid precedent), `gap-4`.

**The EAFC card (D-01/D-02):**

```
┌──────────────────────────────┐  ← border-2 in TIER_BORDER[tierForOvr(rounded ovr)]
│  OVR                  [Tank] │  ← "OVR" 14px text-muted · function badge top-right
│  87                    14px  │  ← text-5xl font-semibold leading-none
│                               │     TIER_TEXT[ovr tier]
│  {display_name}        20px   │  ← text-xl font-semibold text-content
│  {char_class}          14px   │  ← text-sm text-muted
│  ───────────────────────────  │  ← border-t border-line
│  6 highlight facets (2×3)     │  ← mini stat rows, each facet tier-styled
└──────────────────────────────┘    by its own points (tierForPoints)
```

- Card container: `rounded-lg border-2 bg-surface p-6` + `TIER_BORDER[ovrTier]` — the literal OvrHero composition (OvrHero.tsx:36–39). If `ovr` were ever null the RPC omits the card, so every card always has a tier.
- Function badge: `rounded-full border px-2 py-0.5 text-sm font-semibold text-muted` (the role-pill pattern reused for function; text `Tank`/`DPS` from `FUNCTION_LABELS`).
- 6 highlight facets (D-01/D-02): compact rows in a 2-column grid (1 column on very narrow screens), each facet = label 14px semibold + formatted value 14px + integer points chip using the StatCard badge anatomy (`rounded-full border px-2 py-1 text-sm font-semibold` + `TIER_BORDER`/`TIER_TEXT` of `tierForPoints(points)`). Points arrive in the payload; nothing is recomputed client-side.
- **Facet ordering rule:** render in server-returned order (points desc). No client re-sort. RNK-02: no "key"/"principal" labeling, no star, no visual weight beyond the tier color — tier color IS the celebration.
- Value formatting: `formatStatValue(value, value_type)` — FLAT plain, PERCENTUAL `%`, identical to the dashboard.
- Insufficient-classes guard: if `sections.length === 0` → single empty-state line (copy table). If a class section exists, it always has ≥ 1 card.

**Accessibility:** each card is an `<article>` with `aria-label` = `{display_name} — {char_class}`; the points chip carries `aria-label="{n} pontos em {label}"`. No interactive elements inside cards (v1: no sharing, no drill-in — SHAR-01 deferred).

### Surface 3 — Personagens staff controls (AUTH-03/AUTH-04; D-08/D-09)

**File:** extend `src/features/admin/CharactersPage.tsx`. Controls are role-differentiated per D-08: the OWNER sees role grant/revoke plus removal/reactivation on member AND officer targets; OFFICERS see Remover/Reativar on `role='member'` rows ONLY — no role grant/revoke buttons, no controls on officer or owner rows. Owner rows render `—` for every viewer.

**Data prerequisite:** `fetchMembers` projection extends to include `active` (column already granted, 0005:31 — explicit projection extension, never `select=*`). `MemberRow` gains `active: boolean`.

**Add-class gate (folded todo, D-09):** the `Nova classe` form renders only for the owner. Officers get no form, no placeholder — the section simply doesn't exist in their DOM. Server policy is the enforcement.

**Per-row staff controls (new column "Controles"):**

- Role control (OWNER viewer only): for `role ∈ {member, officer}` targets — a **pair of small outline buttons** `Conceder oficial` / `Revogar oficial` (NOT a select; state is unambiguous, confirmation copy differs per direction). Officer targets are owner-only territory. Owner rows (`role === 'owner'`): no role control, render `—`. Officer viewers: no role control anywhere (render `—` on those cells). (auto-resolved: buttons over select)
- Removal control (role-differentiated per D-08):
  - Owner viewer: `role ∈ {member, officer}` targets get **Remover** (when `active === true`) → confirm modal (copy table) → `setMemberActive(member, false)` → success line `Membro removido.` → refetch; **Reativar** (when `active === false`) → single confirm `Reativar {display_name}?` → `setMemberActive(member, true)` → success `Membro reativado.`
  - Officer viewer: SAME Remover/Reativar affordances on `role === 'member'` targets ONLY. Officer and owner target rows render `—` for officer viewers (D-08: "Officers deactivate/reactivate ordinary members. The owner grants/revokes officers and removes officers.").
  - Owner rows: no removal control, render `—` for every viewer.
- Inactive-row visual state: the whole `<tr>` gets `opacity-60` (StatCard missing-state precedent) for staff viewers (owner or officer — both see actionable inactive rows) so deactivated members are scannable at a glance without a new color. (auto-resolved)
- Confirmation modal pattern (reserving 01-UI-SPEC's promise): a fixed-overlay dialog `bg-dominant/80` backdrop, centered `bg-surface border border-line rounded-lg p-6 max-w-sm`, title 16px semibold, body 14px text-muted, actions right-aligned: destructive/primary confirm + `Cancelar`. Role-change confirms use direction-matching confirm labels (`Conceder oficial` / `Revogar oficial`); Reativar confirm uses the `Reativar` label. Focus moves to the confirm button on open; `Escape` and backdrop click cancel. Implemented as one shared local component (e.g. `src/features/admin/ConfirmDialog.tsx`) reused by both Validações and Personagens. (auto-resolved)
- Per-row state machine: reuse `savingRowId`/`savedRowId`/`saveErrorRowId` conventions; role actions and removal actions share the same single-flight `busy` lock.
- D-10 copy duty: every role-change success line says "Efetivo no próximo login." — the stale-JWT caveat is visible in the UI, not just documented.

## Responsive & Mobile-First Contract

- All three surfaces live inside the locked `max-w-3xl px-4 py-6` column. Nothing exceeds 3xl width.
- Queue rows stack naturally (single column); expanded action buttons go **full-width, stacked** on mobile (`flex flex-col gap-2 sm:flex-row sm:justify-end`).
- Promotion grid 1→2→3 columns; card padding `p-6` holds at all sizes (verified readable at 320px: 6 facets at 2-col grid ≈ 130px/facet).
- Personagens table already scrolls horizontally (`overflow-x-auto`) — the new Controles column extends this table; no separate mobile layout is built.
- Modals: `max-w-sm` centered; on very narrow screens they become near-full-width with 16px margins.

## Accessibility Contract

- Tab buttons: `aria-current="page"` on the active tab (existing pattern).
- Queue row toggle: `aria-expanded` + `aria-controls` pointing at the expanded region id.
- Modals: `role="dialog"` `aria-modal="true"` `aria-labelledby` → title; Escape closes; focus trapped to the dialog while open; focus returns to the trigger on close.
- Errors: `role="alert" aria-live="polite"` on every error line (existing convention).
- Success lines: `aria-live="polite"`.
- All buttons/inputs `h-11` (44px targets); focus-visible ring-2 ring-accent everywhere.
- Inactive member rows: `aria-disabled` semantics via the opacity treatment plus the explicit "Inativo" hint in the Controles cell is NOT needed — the Reativar button itself communicates state; keep it simple. (auto-resolved)
